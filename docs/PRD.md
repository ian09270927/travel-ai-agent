# PRD｜旅行社獲客網站
版本：v0.2｜日期：2026-10-19｜狀態：規格與驗收清單，尚未開發

依據：[CCI](CCI.md)、[SIPOC](SIPOC.md)、[上午旅遊資料](../research/travel-data.json)、[來源紀錄](../research/sources.md) 與 [週報](weekly-report.md)。

本版依最新使用者要求更新 v0.1：**改用獨立的本地模擬行程，讓旅伴、預算、天數與風格實際參與推薦**。下文取代舊版「預算與天數只作諮詢記錄」的策略。既有真實研究資料不修改。

## 1. 產品目標

協助親子、情侶與熟齡旅客，以四項明確條件縮小選擇，理解推薦原因、比較候選，最後產生諮詢需求單。

第一版是可操作的獲客流程示範，不是可訂購的旅行社商店。推薦由前端規則完成，不呼叫大模型，不宣稱即時 AI 行程規劃。

### 產品成果與邊界

- 旅客可完成「選條件 → 推薦 → 比較 → 需求單」。
- 旅伴、預算上限、天數均有明確篩選作用；風格影響合格與排序。
- 只用 HTML、CSS、JavaScript 與本地資料，不使用 Supabase、不建立帳密系統、不呼叫需要付費的 API。
- 不建後端、資料庫、付款、訂位、寄信、LINE 通知、CRM 或公開部署。
- 本版不收集真實名單。需求單產生與業務收到名單是兩件事。
- 本階段只編製規格，沒有建立網站或模擬資料程式檔。

未有營運證據，不設定虛構市場規模或宣稱成交增加。未來可量測表單完成、推薦產生、需求單產生等事件，但本版不裝追蹤器，也不把需求單產生視為成交。

## 6. 資料策略與欄位

### 6.1 真實資料與模擬資料分開

上午研究共有 9 筆：6 個景點、3 項活動，查詢日 2026-10-19。沒有可核實的套裝行程總價及天數。本版因此規劃獨立的本地模擬商品，不回填原研究的價格欄。

開發時可新增 `website/data/mock-plans.json` 或等價的本地 JS 資料模組；本次只定義規格，不建立該檔。來源特色與活動日期可引用上午資料，模擬價格、天數、商品名稱與每日安排須分別標註。

網站固定揭露：

> 教學示範：行程、價格與天數為模擬，非旅行社報價。實際活動、費用、開放與交通須另行確認。

來源連結命名為「官方景點／活動資訊」，不能寫成「官方行程報價」。不存在的優惠、營業時間、班次與活動日期不自行補入。

### 6.2 使用者偏好欄位

| 欄位 | 型別／介面 | 驗證與用途 |
|---|---|---|
| `audience` | enum，單選 family／couple／senior | 必填，畫面對應親子／情侶／熟齡。 |
| `budget_mode` | enum limited／undecided | 必填；「尚未決定」為獨立狀態，不能與金額 0 混用。 |
| `budget_per_person_twd` | 正整數或 null | limited 時必填正整數；undecided 時為 null。單位為每人、整趟、新台幣。 |
| `days` | integer，1／2／3 天 | 必填，精確比對示範天數。 |
| `styles` | enum array，1–2 項 | 必填，nature／culture／scenic／music，對應自然生態／文化藝文／景觀慢遊／音樂活動。 |
| `departure_date` | YYYY-MM-DD 或 null | 選填，實際日曆有效且不早於 Asia/Taipei 當日；影響活動型方案。 |
| `notes` | string，最多 300 字 | 選填，僅納入需求單，不用關鍵字暗自改變篩選。提醒不要填個資。 |

不收姓名、電話、Email、證件、健康診斷或付款資料。天數 1–3 天與風格選項是產品設計，不是官方旅遊限制。

### 6.3 模擬行程欄位

| 欄位 | 型別與要求 |
|---|---|
| `id` | 唯一字串，如 MOCK-01；不得與研究 TW-001 等 ID 混用。 |
| `title`、`region` | 教學方案名稱與地區；名稱標示為示範。 |
| `audiences` | 合法客群陣列，與所引用研究的推薦方向一致。 |
| `days` | 1–3 的整數，屬模擬。 |
| `demo_price_per_person_twd` | 大於 0 的整數，屬模擬「每人整趟總額」，不拿單張門票冒充總價。 |
| `styles` | 至少一個合法風格標籤，為企劃分類。 |
| `highlights` | 來源特色摘要；創作內容另標明，不混成官方事實。 |
| `itinerary_outline` | 每日提綱陣列，長度等於 days；標為模擬安排。不可自行填營業時間、交通班次與真實服務承諾。 |
| `research_ids` | 對應真實研究 ID，至少一筆，可追查地區、特色及限制。 |
| `event_requirements` | 陣列；每筆含研究 ID 與 `day_index`（第幾天），活動起訖從原研究取值。常設景點方案為空陣列。 |

| `mock_fields` | 至少列 title、days、demo_price_per_person_twd、itinerary_outline。 |

| `image`、`image_kind` | 可選本地素材；kind 為 ai_illustration 等，需有可見說明，不把示意圖當實拍。 |

原研究的來源 ID、網址、查詢日及更新日應能由 `research_ids` 取得；更新日未知就顯示未知，不用網站開啟日代替。必要欄位缺漏或研究 ID 無法對應的方案不能進入推薦。

### 6.4 需求單欄位

包含資料模式 `mock`、四項偏好、日期與備註、選定 MOCK ID／名稱、示範價格／天數、實際命中的理由、引用來源與查詢日、待確認事項，以及「尚未傳送給旅行社」。

需求單以純文字顯示與下載，沒有伺服器編號或受理成功狀態。產生時間可以記錄，但不得標為官方查證時間。

## 8. 推薦邏輯

### 8.1 驗證、篩選與排序

1. 驗證輸入及本地資料；只處理 `is_mock === true` 且必要欄位有效的方案。
2. 旅伴：方案 audiences 必須包含所選旅伴。
3. 天數：方案 days 必須等於輸入 days，不提供擅自延長或縮短的替代。
4. 預算：limited 模式下，示範總價必須小於或等於預算上限；undecided 模式略過價格篩選並明示「預算尚未決定」。
5. 風格：至少符合一項所選風格；若只符合一項，理由只列該項，不能說全部符合。
6. 日期：常設景點方案不要求出發日。有限定活動的方案，沒填日期即排除；計算出發日加上 day_index−1，該天須落在來源起訖內（含邊界）。結束日早於執行當日的活動排除。缺少或無效日期也排除。
7. 排序依「符合風格項數多者優先 → 示範總價低者優先 → ID 字典順序」，輸出前 3 筆。這是規則，不是官方評等或適合度百分比。
8. 依實際命中欄位組合固定文字理由，例如「符合親子、1 天、示範預算上限與自然生態偏好」。同時保留非報價揭露。
9. 沒有結果就顯示空狀態，讓旅客主動改條件；不能自動改旅伴、加預算或捏造商品補滿。

活動期間符合只能說「日期落在公告期間，實際場次待確認」，不能保證演出。網站的今天以 Asia/Taipei 計算；不讓已結束活動為了教學一直保持可推薦。

### 8.2 狀態一致性

偏好任一欄修改時，舊結果、比較、候選與需求單立即標記失效，停用匯出並提示重新推薦。重新推薦完成後才建立新的條件快照。不把舊候選套到新預算，也不以備註偷偷改變推薦。

比較最多 3 筆。諮詢候選從當次推薦中選 1–3 筆，可與比較選擇不同，但不能引用其他輪次結果。

## 9. 響應式設計與無障礙

- 台灣繁體中文，深綠／奶油白／暖橘延續簡報風格，使用本機字型，無外部字型依賴。
- 360–767 px：單欄卡片、欄位上下排列、比較資訊依方案堆疊；不靠橫向捲動才能看完主要內容。
- 768–1199 px：可採兩欄，表單與結果保持閱讀順序。
- 1200 px 以上：最多三欄結果與比較，內容有最大寬度。
- 一般正文至少 18 px，按鈕有效區域至少 44×44 px；文字可放大到 200%，焦點與內容仍可操作。
- 表單使用 label、fieldset／legend 等語意；錯誤對應欄位，結果更新可由輔助技術得知。
- 詳情用可鍵盤操作的展開區；若採對話框，須處理焦點、關閉與返回觸發按鈕。
- 不只用顏色表示選取、錯誤或模擬狀態；支援減少動態偏好。
- 影片保留 controls、playsinline，預設 preload=metadata，不自動播放聲音。圖片保留尺寸與替代文字；AI 圖不當作實拍。
- 控制項不可被固定 CTA 遮住，手機切換橫直向不遺失當次合法輸入。

## 10. 錯誤情況與恢復

| 狀況 | 預期行為 |
|---|---|
| 必填未選、預算 0／負數／小數、天數非法、超選風格 | 在欄位旁顯示原因，焦點移到首個錯誤，不產生推薦。 |
| 日期格式錯誤、不存在或早於今天 | 提示修正；不以瀏覽器自動進位替代錯誤日期。 |
| 本地資料讀不到或解析失敗 | 顯示資料錯誤與重試，保留表單；不臨時換成未標示資料。 |
| 單筆無價格、天數錯誤、ID 重複或研究關聯不存在 | 不參與推薦，保留可用紀錄；無可用資料時呈現資料錯誤，不冒充正常空結果。 |
| 四項條件交集為空 | 顯示「目前沒有符合條件的示範行程」，指出可修改條件，不擅自放寬。 |
| 限定活動但未選日期或日期不符 | 排除活動型方案；若只選音樂風格且無日期，提示先選日期，不暗示全年可用。 |
| 加入第 4 筆比較 | 提示上限，保留原 3 筆。 |
| 未選諮詢候選 | 停用產生按鈕或顯示至少選一筆的提示。 |
| 剪貼簿拒絕或不支援 | 顯示可選取純文字與下載，不宣稱複製成功。 |
| 圖片／影片失敗 | 顯示文字替代與重試，推薦流程仍可使用。 |
| 更新偏好後仍有舊結果 | 顯示已失效，重新推薦前不可匯出。 |
| 本機瀏覽限制 | 推薦用本機 HTTP 啟動；若採 JSON fetch，說明 file:// 限制與正確啟動方式，不將它誤報成資料損壞。 |

## 11. 隱私考量

- 第一版不收真實聯絡資料，不使用帳密、第三方分析、雲端儲存或任何 API 金鑰。
- 偏好、備註、比較與需求單只留在頁面記憶體，不放 localStorage、IndexedDB、cookie、網址查詢字串或應用日誌。
- 重新整理或按「清除需求」重設使用者輸入；下載或複製只在旅客主動點擊時發生，不自動執行。
- 備註提醒「請勿輸入姓名、電話、Email、證件或健康資料」。顯示一律當純文字，不執行輸入內容。
- 沒有對外送出需求的請求。官方來源連結由使用者主動開啟；頁面要清楚區別外部資訊與本機需求單。
- 不收聯絡資料，因此不使用預先勾選的行銷同意來製造名單。未來真正獲客收件需另定用途、同意、保存與刪除流程，再經授權串接。

## 13. 技術與交付規劃

後續開發使用原生 HTML、CSS、JavaScript，無框架與建置工具也能執行；可使用本機 HTTP 伺服器提供靜態檔案。資料檔與素材全部置於本地，沒有外部資料庫或付費服務依賴。

預計實作產物為網站入口、樣式、互動腳本、本地模擬資料、啟動 README 與驗收紀錄。檔名及結構於開發時落實，本階段不先建立空殼檔案。

完成定義：所有必須功能有實際瀏覽器流程證據，推薦規則與錯誤案例可重現，桌面／手機已視覺檢視，並分別記錄通過、未通過及未驗證。檔案存在不等於功能通過，網站可在本機使用不等於公開上線。

建議開發順序：資料與規則 → 表單及結果 → 比較與需求單 → 響應式／錯誤／隱私檢查 → 驗收。需求變更時先更新三份文件，再調整功能。
