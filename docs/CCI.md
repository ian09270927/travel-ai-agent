# CCI｜旅行社獲客網站需求定義

版本：v0.2｜日期：2026-10-19｜狀態：規劃完成，尚未開發

本文件與 [SIPOC](SIPOC.md)、[PRD](PRD.md) 配套。以本次使用者要求為優先：第一版使用 HTML、CSS、JavaScript 與本地模擬資料；不使用 Supabase、帳密系統或付費 API。

## Core｜核心

協助旅客依照**旅伴、每人整趟預算、天數與旅遊風格**，從少量可解釋的推薦行程中找到適合討論的候選，接著產生可交給旅行社的諮詢需求單。

旅客的價值是減少比較負擔，旅行社的價值是讓詢問內容更完整。這是產品目標，不是已證實的轉換率或業務成效。

第一版演示獲客流程到「產生與匯出需求單」。沒有外部收件服務，不宣稱旅行社已收到名單。

## Clear｜明確

| 編號 | 可執行需求 | 驗收對應 |
|---|---|---|
| C01 | 旅伴可選親子、情侶、熟齡；預算用新台幣「每人整趟」表示；天數選 1、2 或 3 天；風格選 1–2 項。 | PRD FR-02、AC-02～04 |
| C02 | 用本地模擬行程的客群、示範價格及天數做真正篩選；風格比對後最多推薦 3 筆。 | FR-03、AC-05～10 |
| C03 | 每筆顯示特色、推薦理由、比較欄位、資料性質與限制。 | FR-04～05、AC-11～12 |
| C04 | 選定候選後，本機產生需求單，可複製及下載，清楚標示尚未傳送。 | FR-06、AC-13～15 |
| C05 | 手機與桌面皆可用；表單、比較及錯誤訊息能以鍵盤操作。 | FR-07、AC-18～19 |
| C06 | 規格與模擬商品和上午官方研究分開；來源網址支持景點特色，不支持模擬價格與天數。 | FR-01、AC-01、AC-20 |

產品必須顯示：「教學示範：行程、價格與天數為模擬，非旅行社報價。」揭露需出現在首頁、推薦卡、比較與需求單，不能只藏在頁尾。

## Issue｜要解決的問題

| 問題 | 解法 | 不應出現的作法 |
|---|---|---|
| 行程太多，不知道怎麼選 | 四項條件縮小範圍，最多展示 3 筆。 | 一次丟出所有資料而沒有說明。 |
| 方案格式不一致，難以比較 | 統一地區、天數、每人示範價、風格、限制與推薦理由。 | 用虛構星等或「95% 適合」取代說明。 |
| 預算與天數看似可選卻沒有作用 | 在獨立模擬商品上做預算上限與天數精確篩選。 | 只收集條件卻宣稱價格已符合。 |
| 上午資料沒有完整行程價格 | 保留真實研究，另定義模擬商品，不補寫官方欄位。 | 把模擬價格歸因於觀光署，或把未知價格當免費。 |
| 有興趣卻不知道如何詢問 | 產生含條件、候選及待查事項的需求單。 | 顯示假的寄送成功或虛構聯絡方式。 |
| 教學期間容易膨脹成大型系統 | 第一版限前端、本地資料與本機互動。 | 提前加入資料庫、登入、付款或付費模型。 |

## 資料基礎與設計假設

上午成果為 [9 筆旅遊研究](../research/travel-data.json)、[來源紀錄](../research/sources.md) 與 [旅遊情報週報](weekly-report.md)。其中價格、營業時間、交通班次尚未核實，客群適合度為研究判斷。

本版的模擬行程只借用有來源的景點名稱及主題特色。預算、天數、商品名稱、每日提綱與組合方式均為教學設計，詳見 PRD 的模擬資料規格。不得據此接受訂單。

## 本階段完成定義

三份文件一致定義目標、供應到顧客的交接、第一版範圍、資料欄位、推薦規則與可重現驗收案例。網站、模擬資料檔、測試程式與部署尚未建立。

教學順序：用 CCI 說清楚「解決什麼」→ 用 SIPOC 說清楚「資料怎麼交接」→ 用 PRD 說清楚「功能怎麼驗收」→ 之後才進入網站實作。
